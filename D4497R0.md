# Abstract

C++ has many kinds of integer. The standard defines standard and extended
integer types, character types and `bool`, enumerations and `std::byte`, and
integer-class types. Compilers add `__int128`, C23 adds bit-precise integers,
and libraries add types of every width and overflow behavior. The standard
library supports these unevenly, since each facility admits its own set of
types. This paper surveys the integer types, the rules that govern them, the
library facilities that accept them, and what three implementations accept in
practice. It then describes them along common axes. It proposes no changes.

# Introduction

Several proposals in flight would add integer types or integer facilities to
C++, among them bit-precise integers, arbitrary-precision integers and new
integer functions ([In progress]). Each paper reviews the existing landscape
from its own angle. This paper
reviews it once, so that later papers and their reviewers can share a common
description of what C++ already has.

[@P1467R9] played a similar role for floating-point types. Before adding new
floating-point types, it set out the standard and extended floating-point
types and the rules for converting among them. This paper does the same
groundwork for integers, but describes rather than proposes.

The built-in integer types differ in ways that matter to every new design:

- Unsigned arithmetic wraps modulo 2^N^.
- Signed overflow is undefined behavior.
- Operands narrower than `int` are promoted, so `uint8_t + uint8_t` has type
  `int`.
- Mixed signed and unsigned operands convert in ways that can change the
  value.

These rules are described in [Behavior of the built-in integer types]. The
library section then shows that each facility in the standard library admits
its own set of types, and the implementation section shows how libc++,
libstdc++ and the MSVC STL handle the types the standard leaves to them.

# Integer types in the core language

## The fundamental integer types

[basic.fundamental] defines five *standard signed integer types*: `signed char`,
`short int`, `int`, `long int`, and `long long int`. An implementation may also
provide *extended signed integer types*. Together these are the *signed integer
types*. Each signed integer type has a corresponding unsigned type of the same
width, giving the *standard unsigned integer types*, the *extended unsigned
integer types*, and together the *unsigned integer types*. The *standard integer
types* are the standard signed and unsigned types; the *extended integer types*
are the extended signed and unsigned types.

The *width* N of a signed integer type is defined by its range, −2^N−1^ to
2^N−1^−1. The corresponding unsigned type has the same width and the range 0
to 2^N^−1, and "arithmetic for the unsigned type is performed modulo 2^N^". The
representation is two's complement, specified as a congruence: a signed value
and the unsigned value congruent to it modulo 2^N^ have the same bits
[@P1236R1]. The value representation has exactly N bits. Any other bits in the
object representation are padding bits, which "have unspecified value, but
cannot cause traps". The width of each type is implementation-defined. The
standard signed types must be at least as wide as the types before them in the
list `signed char`, `short`, `int`, `long`, `long long` ([conv.rank]). They are
also subject to these minimums:

| Type | Minimum width |
|:--|:-:|
| `signed char` | 8 |
| `short int` | 16 |
| `int` | 16 |
| `long int` | 32 |
| `long long int` | 64 |

The other fundamental types that hold integers are defined in terms of these:

- **Character types.** These are `char`, `wchar_t`, `char8_t`, `char16_t` and
  `char32_t`. Each is a distinct type with an *underlying type*:
  - `char`: `signed char` or `unsigned char`, implementation-defined
  - `wchar_t`: an implementation-defined signed or unsigned integer type
  - `char8_t`: `unsigned char`
  - `char16_t`, `char32_t`: `uint_least16_t` and `uint_least32_t`

  `char`, `signed char` and `unsigned char` are the *ordinary character types*;
  with `char8_t` they are the *narrow character types*. `signed char` and
  `unsigned char` are therefore both ordinary character types and signed or
  unsigned integer types. They are not "character types".
- **`bool`.** It has the representation of an implementation-defined unsigned
  integer type, and its values are `true` and `false`.

[basic.fundamental] then groups all of these: "The character types, `bool`, the
signed and unsigned integer types, and cv-qualified versions thereof, are
collectively termed *integral types*. A synonym for integral type is *integer
type*." So when the standard says "integer type" it includes `bool` and the
character types. Library wording that means only the arithmetic integers says
"signed or unsigned integer type" instead. [@P3701R0] proposes giving the two
terms distinct meanings.

The resulting classification is:

```default
integral types (also called integer types), and cv-qualified versions
├── bool
├── character types: char, wchar_t, char8_t, char16_t, char32_t
└── signed and unsigned integer types
    ├── standard integer types
    │   ├── signed:   signed char, short, int, long, long long
    │   └── unsigned: unsigned char, unsigned short, unsigned int,
    │                 unsigned long, unsigned long long
    ├── extended integer types (implementation-defined)
    └── [proposed by P3666R5] bit-precise integer types:
                      _BitInt(N), unsigned _BitInt(N)
```

Integral and floating-point types are together the *arithmetic types*.

Every integer type has an *integer conversion rank* ([conv.rank]). Rank
increases with width; `long long` outranks `long`, which outranks `int`,
`short` and `signed char` in that order. A standard integer type outranks an
extended integer type of the same width. An unsigned type has the rank of its
signed counterpart, a character type has the rank of its underlying type, and
`bool` has the lowest rank. In N5054 these rules were reworded by CWG3168,
applied as a Defect Report through [@P4271R0]. The rank of `char` now follows
from its underlying type, which does not change it. `bool` now ranks below all
other integer types, including extended ones. Before, it ranked below the
standard integer types only.

## Integers outside the fundamental integer types

### Enumerations and `std::byte`

Enumerations are not integral types, but each has an integral *underlying
type* ([dcl.enum]). The underlying type is *fixed* if it is written explicitly
or if the enumeration is scoped (where it defaults to `int`). Otherwise it is
an implementation-defined integral type that can represent all the
enumerators, not larger than `int` unless necessary. For a fixed underlying
type, the enumeration's values are the values of that type. Otherwise they are
the values of the narrowest hypothetical integer type that holds all the
enumerators, and a `static_cast` of a value outside that set is undefined.

Unscoped enumerations take part in integral promotion, and so in arithmetic
([conv.prom]). If the underlying type is not fixed, an unscoped enumeration
promotes to the first of `int`, `unsigned int`, `long`, `unsigned long`,
`long long` and `unsigned long long` that can represent all its values. If it
is fixed, the enumeration promotes to the underlying type and then as that type
does. A scoped enumeration does not take part in promotion or the usual
arithmetic conversions. Mixing an enumeration with a different
enumeration or with a floating-point type in arithmetic is ill-formed in C++26
([diff.cpp23.expr]); it was deprecated before that.

`std::byte` is `enum class byte : unsigned char {}` ([cstddef.syn]). It has
bitwise operators and shifts but no arithmetic. Its shift operators and
`to_integer` are constrained on `is_integral_v<IntType>`, which admits `bool`
and the character types ([support.types.byteops]).

### Bit-fields

A bit-field has integral or enumeration type and a width, which may be smaller
than the width of its type ([class.bit]). If the width is larger than the
type's width, the extra bits are padding. Promotion uses the bit-field's
width, not its type: an `unsigned int` bit-field of width 31 promotes to `int`
([conv.prom]). Narrowing has a matching exception ([dcl.init.list]).

### Integer-class types

[@P1522R1] added *integer-class types* for C++20, so that a range such as
`views::iota(0LL, n)` can have a difference type wider than any integral type
([iterator.concept.winc]). Integer-class types are an implementation-defined
set of types that "behave as integer types do". They are the only types in the
standard described as behaving like integers without being integral. The
requirements are:

- **Width:** greater than that of every integral type of the same signedness.
  A signed-integer-class type has range −2^N−1^ to 2^N−1^−1; an
  unsigned-integer-class type has range 0 to 2^N^−1.
- **Behavior:** each operation behaves as it would on a hypothetical extended
  integer type of the same width and signedness.
- **Conversions:** explicit to any integer-like type, implicit to
  integer-class types of the same signedness and equal or greater width, and
  implicit from integral types.
  Conversions never throw and are modulo 2^N^.
- **Library support:** `numeric_limits` must be specialized, and
  `common_type` with other integer-like types is defined.
- **Integer-like:** the term means "integral other than `bool`, or
  integer-class".

An integer-class type need not be a class type. The standard library may define
integer-class types, but a program cannot add to the set. The MSVC STL uses
`std::_Signed128` and `std::_Unsigned128`. libstdc++ uses `__int128` where it
is wide enough, as for `iota_view<long long>`, and the class types
`__max_diff_type` and `__max_size_type` for wider cases. libc++ uses `__int128`.

### Type aliases

`<cstdint>` declares the same aliases as C's `<stdint.h>`, with two
differences ([cstdint.syn]):

- `intptr_t` and `uintptr_t` are always defined. This is new in the C++29
  working draft [@P3248R5]; in C++26 they are optional.
- `intmax_t` and `uintmax_t` "are not required to be able to represent all
  values of extended integer types wider than `long long`". This lets an
  implementation add wider extended integer types without changing
  `intmax_t`, a type that appears in the signatures of functions such as
  `imaxabs`.

The `int_leastN_t` and `int_fastN_t` aliases for N = 8, 16, 32 and 64 are
required. The exact-width aliases `int8_t` through `int64_t` and their
unsigned counterparts are optional, but must be declared if the
implementation has a type of that width with no padding bits. Aliases for any
other N are optional. [@P4378R0] proposes requiring `intN_t` for every width
that has a suitable type, as C23 does.

Other aliases name an implementation-defined integer type with a stated
purpose:

- **`size_t`, `ptrdiff_t`:** an unsigned and a signed integer type, with
  recommended rank no greater than `long` unless a larger size is needed
  ([support.types.layout]).
- **`streamoff`, `streamsize`:** "signed basic integral types" ([stream.types]),
  a term the standard does not define.

Many library templates add member aliases, such as `size_type`,
`difference_type` and `rep`.

### Integer literals

The type of an integer literal is the first type in a list that can represent
its value ([lex.icon]). The list depends on the suffix and on whether the
literal is decimal:

| Suffix | Decimal literal | Binary, octal or hexadecimal literal |
|:--|:--|:--|
| none | `int`, `long`, `long long` | `int`, `unsigned`, `long`, `unsigned long`, `long long`, `unsigned long long` |
| `u` | `unsigned`, `unsigned long`, `unsigned long long` | same |
| `l` | `long`, `long long` | `long`, `unsigned long`, `long long`, `unsigned long long` |
| `ul` | `unsigned long`, `unsigned long long` | same |
| `ll` | `long long` | `long long`, `unsigned long long` |
| `ull` | `unsigned long long` | same |
| `z` | signed type corresponding to `size_t` | that type, then `size_t` |
| `uz` | `size_t` | same |

If no listed type can represent the value, the literal may have an extended
integer type; otherwise the program is ill-formed. The `z` and `uz` suffixes
are new in C++23 [@P0330R8]. No suffix produces a type narrower than `int`;
[@P1280R2] proposed width suffixes. C23 has the suffixes `wb` and `uwb` for
bit-precise integers, which [@P3666R5] proposes to adopt.

# Behavior of the built-in integer types

This section describes the rules that apply to the built-in integer types in
expressions. The examples assume 8-bit `char`, 16-bit `short`, 32-bit `int`
and 64-bit `long long`. Every example is checked by
[`probes/D4497R0/behavior.cpp`](https://github.com/mborland/wg21-papers/blob/main/probes/D4497R0/behavior.cpp).

## Promotions and conversions

**Integral promotions** ([conv.prom]):

- An integer type of rank lower than `int` is converted to `int`, or to
  `unsigned int` if `int` cannot hold all its values. The exceptions are
  `bool`, `char8_t`, `char16_t`, `char32_t` and `wchar_t`.
- `char8_t`, `char16_t`, `char32_t` and `wchar_t` are converted to the first
  of `int`, `unsigned int`, `long`, `unsigned long`, `long long` and
  `unsigned long long` that can hold all their values.
- `bool` is converted to `int`.
- Bit-fields and unscoped enumerations follow the rules described above.

**The usual arithmetic conversions** ([expr.arith.conv]) promote both operands
of most binary operators, then convert them to a common type:

- If both have the same signedness, the common type is the one of higher rank.
- Otherwise it is the unsigned type if that type's rank is at least the signed
  type's rank.
- Otherwise it is the signed type, if that type can represent every value of
  the unsigned type.
- Otherwise it is the unsigned type corresponding to the signed type.

The common type of `long` and `unsigned int` is therefore `long` where `long`
is 64 bits and `unsigned long` where it is 32 bits.

**Integral conversions** ([conv.integral]) produce "the unique value of the
destination type that is congruent to the source integer modulo 2^N^". This
holds for signed destination types too, so integer-to-integer conversion is
never undefined. Before C++20 the result for a signed destination was
implementation-defined.

**Floating-integral conversions** ([conv.fpint]): converting a floating-point
value to an integer type truncates, and is undefined if the truncated value
does not fit. Converting an integer to a floating-point type that cannot
represent it exactly picks the next lower or higher value; the result is
undefined only if the value is out of range.

**Narrowing conversions** ([dcl.init.list]) make list-initialization
ill-formed. Between integer types, a conversion is narrowing if the target
cannot represent all values of the source, unless the source is a constant
expression whose value fits.

## Overflow

N5054 defines an *arithmetic expression* as unary `+` or `-`, or binary `+`,
`-`, `*`, `/` or `%`, with operands of arithmetic type. "The behavior of
evaluating an arithmetic expression is undefined if the mathematical result is
neither in the range of representable values for its type nor" an infinity or
NaN of the type ([expr.pre]). This wording comes from [@P3899R3], applied as a
Defect Report. The C++26 text in [@N5050] says instead that the behavior is
undefined if "the result is not mathematically defined or not in the range of
representable values for its type". Under either wording, signed integer
overflow is undefined.

Unsigned arithmetic is modular ([basic.fundamental]). Because operands are
promoted first, an operation on unsigned types narrower than `int` happens in
`int` and can overflow. Converting the result back to a narrow type is modular:

```cpp
std::uint8_t{200} + std::uint8_t{100}      // int, 300
std::uint16_t{65535} * std::uint16_t{65535} // int overflow: undefined
std::int8_t x = 127; ++x;                   // x == -128 (computed in int, then converted)
```

Compound assignment and `++`/`--` are defined in terms of `E1 = E1 op E2`, so
they inherit both the promotion and the conversion.

## Division and remainder

Integer division truncates toward zero ([expr.mul]). If the divisor is zero,
the behavior is undefined. If the quotient cannot be represented, as in
`INT_MIN / -1`, then both `a / b` and `a % b` are undefined. `std::div` and
its variants return the quotient and remainder with the same truncation. No
standard function divides with another rounding direction; [@P3724R4] proposes
such functions.

## Shifts

Each operand of `<<` and `>>` is promoted separately, and the result has the
type of the promoted left operand ([expr.shift]). The usual arithmetic
conversions are not applied. The behavior is undefined if the right operand is
negative or is at least the width of the promoted left operand. Otherwise,
since C++20:

- `E1 << E2` is the value congruent to E1 × 2^E2^ modulo 2^N^, so shifting
  into or out of the sign bit is defined.
- `E1 >> E2` is E1 / 2^E2^ rounded toward negative infinity.

The C++29 working draft adds `std::shl` and `std::shr` ([bit.shift],
[@P3793R2]). They accept any signed or unsigned integer type for either
operand, and have no undefined shift counts.

## Comparisons

Relational and equality operators apply the usual arithmetic conversions
([expr.rel]), so `-1 < 0u` is `false`. The three-way comparison operator is
ill-formed if a narrowing conversion other than integer-to-floating is
required, so `-1 <=> 0u` does not compile ([expr.spaceship]). It is also
ill-formed if exactly one operand is `bool`. The functions `cmp_less` and its
siblings ([utility.intcmp]) compare the mathematical values.

## Constant evaluation

An expression is not a core constant expression if it performs an operation
that would have undefined or erroneous behavior as specified in the core
language clauses, [intro] through [cpp] ([expr.const.core]). Signed overflow,
division by zero and an out-of-range shift are therefore compile-time errors
when they occur during constant evaluation. For undefined behavior in the library clauses, it is
unspecified whether the expression is a core constant expression.

## Other rules

- **Atomics:** for signed integer types, `fetch_add` and the other atomic
  arithmetic operations behave as if the operands were converted to the
  corresponding unsigned type and the result converted back
  ([atomics.ref.int], [atomics.types.int]). A note says "There are no undefined
  results arising from the computation." The same signed addition with the
  built-in `+` operator is undefined on overflow.
- **Erroneous behavior:** C++26 makes reading an uninitialized automatic
  variable erroneous behavior rather than undefined behavior [@P2795R5].
  Integer overflow remains undefined, not erroneous.
- **Library hardening:** hardened preconditions ([structure.specifications])
  are bounds and state checks. None of them applies to built-in integer
  arithmetic.
- **The undefined-behavior annex:** the C++29 working draft adds an
  informative annex [ub] listing core undefined behavior [@P3596R3], including
  division by zero, an unrepresentable quotient, out-of-range shifts and
  out-of-range floating-integral conversions. The editors' report [@N5055]
  notes that the annex has not yet been updated for the other motions applied
  at the same meeting. Its entry for [expr.pre], for example, still has the
  wording that [@P3899R3] replaced.

# Library support for integers

Library facilities that take integers do not agree on which integers they
take. Some use the core term *integral type*, which includes `bool` and the
character types. Some use *signed or unsigned integer type*, which excludes
them. Some admit only unsigned types, and some give a fixed list of standard
types. The choice decides whether extended integer types, character types and
`bool` are accepted, and whether a type added later to one of those categories
is accepted without further wording.

## Which types each facility admits

In the table:

- **Extended** is whether extended integer types are admitted.
- **Character** covers `char`, `wchar_t`, `char8_t`, `char16_t` and
  `char32_t`. `signed char` and `unsigned char` are signed and unsigned integer
  types, so they are admitted wherever those are.
- *Promoted* means there is no overload for the type, but an argument reaches
  an `int` overload by integral promotion.

All wording is from [@N5054]. Facilities marked *C++29* are new in that
working draft.

Some details matter when reading the table:

- **`signed char` and `unsigned char` are treated inconsistently.** Most
  facilities treat them as integers. iostreams insert them as characters,
  deprecated in the C++29 working draft [@P3154R3]. `<random>` admits them as
  `IntType` since C++26 [@P4037R1], but `unsigned char` is not a valid
  `UIntType`.
- **Wide extended integer types fall outside some limits.** `basic_format_arg`
  stores an integer wider than `long long` as a `handle`, and dynamic width
  and precision accept only standard integer types ([format.string.std]).
  `intmax_t` need not represent extended integer types wider than `long long`.
  `abs(intmax_t)` exists only if `intmax_t` is an extended integer type.
- **Some functions are not `constexpr`.** All functions in the table are
  `constexpr` except those in `<stdckdint.h>` and `<stdbit.h>`, `hash`,
  `<random>`, iostreams, `stoi` and related functions, and some `<cmath>`
  functions. The `<cmath>` exceptions are `nearbyint`, `rint`, `lrint`,
  `llrint` and the mathematical special functions.
- **Some facilities are not available freestanding.** The facilities that are
  not freestanding are `<stdckdint.h>`, `<cmath>` (except integer `abs`),
  `<cinttypes>`, `to_string` and `stoi` and related functions, `<format>`,
  iostreams, `bitset`, `<chrono>`, `simd` and `complex`.
- **Constraints or Mandates.** Some facilities restrict their types with
  *Constraints*, so an unsuitable type removes the overload: `<bit>`,
  `byteswap`, `midpoint` and saturation arithmetic. Others use *Mandates*:
  `cmp_equal` and related functions, `in_range`, `gcd`, `lcm`, `ckd_add` and
  related functions, the `stdc_` functions, `make_signed`, `make_unsigned` and
  `extents`. Using one of these with an unsuitable type makes the program
  ill-formed, but the overload need not be removed, so a `requires` test may
  still succeed. Implementations differ here: libc++ removes `cmp_less` for
  `char`, while libstdc++ does not.
- **Facilities declare their overloads in three ways.** This decides whether
  they would accept a new integer type automatically:
  - a fixed set of overloads, relying on promotion (`abs`, `to_string`,
    iostreams);
  - one overload per type in a category (`to_chars`, `from_chars`);
  - a template restricted to a category (`<bit>`, saturation arithmetic,
    `cmp_less`).

  A new fundamental type in a category reaches the third form without new
  wording. It reaches the second if the new types are a finite set, but a
  family such as `_BitInt(N)` needs templates; [@P3666R5] adds `to_chars` and
  `from_chars` templates for it. The first form needs new overloads.
  For iostreams, arithmetic insertion and extraction go through the virtual
  member functions of `num_put` and `num_get`. These are also a fixed set of
  types ([facet.num.put.virtuals], [facet.num.get.virtuals]).

## How a class type participates

A program-defined class type that behaves like an integer cannot become an
integral type. It can reach a library facility in one of four ways:

- **Excluded.** The program may not specialize the type traits ("the
  behavior of a program that adds specializations for any of the templates
  specified in [type.traits] is undefined", [meta.rqmts]). Concepts cannot be
  specialized at all. A class type is therefore never `is_integral`, never
  `std::integral`, and cannot be passed to any facility constrained on those
  or on *signed or unsigned integer type*. Integer-class types are the only
  class types treated as integer-like, and only the implementation can define
  them.
- **Specialization.** A program may specialize a standard class template for a
  program-defined type ([namespace.std]). This covers `numeric_limits`,
  `hash` and `formatter`, as well as `common_type` and `chrono::duration_values`.
- **Requirements.** Some facilities state requirements rather than a list of
  types:
  - `chrono::duration` accepts "a class emulating an arithmetic type";
  - `iota_view` accepts any weakly incrementable type;
  - `abs-if-needed` in `<linalg>` finds `abs` by argument-dependent lookup.
- **Own functions.** For most other facilities, such as `gcd`, `popcount`,
  `to_chars`, `saturating_add` and `cmp_less`, the program cannot add
  overloads, because adding declarations to namespace `std` is undefined. A
  class type can provide same-named functions in its own namespace. Those are
  found only by unqualified calls. The `<random>` templates cannot take a class
  type as `IntType` at all ([rand.req.genl]).

A class type specified by the standard is different, because the standard can
add the overloads itself. [@P0539R5] proposed `to_chars`, `from_chars` and
`hash` for `wide_integer`. [@P4444R1] proposes `gcd`, `lcm`, `midpoint`,
`in_range`, `saturating_cast`, `abs`, `to_chars` and `from_chars` for
`big_int`.

# A descriptive taxonomy

The standard classifies integer types by how they are declared: standard,
extended, character, and so on. Integer types are compared in design
discussions along other lines, such as width, overflow behavior, conversion
rules and object model. This section names those lines so that the types in
this survey can be placed side by side. The axes describe existing designs;
they are not proposed terms.

## Axes

**Range.** The set of values a type can hold:

- **minimum width:** the width is chosen by the implementation, above a
  guaranteed minimum (`int`, `long`).
- **exact width:** the width is fixed and known (`int32_t`, a 128-bit class
  type).
- **bit-precise:** the program chooses any width N (`_BitInt(N)`, a class
  template with a width parameter).
- **run-time width:** each object has a width fixed when it is created.
- **bounded:** the values are a range [*a*, *b*] chosen by the program,
  usually at compile time, and need not be a power of two.
- **unbounded:** the width grows with the value. It is limited only by memory.

**Representation.** Two's complement, unsigned binary, or sign and magnitude.
A sign-and-magnitude type may still define bitwise operations as if on an
infinite two's complement representation.

**Out-of-range result.** What happens when the mathematical result of an
operation is not a value of the type:

- **undefined:** the program has undefined behavior.
- **wrap:** the result is reduced modulo 2^N^.
- **saturate:** the result is clamped to the nearest representable value.
- **report:** the result comes with an indication of overflow, such as a
  `bool`, an `optional`, a pair, or an invalid state in the object.
- **throw:** an exception is thrown.
- **terminate:** the program stops, as with a trap, `abort`, `exit` or
  `std::terminate`.
- **widen:** the result has a wider type, so the result is always in range.
- **not applicable:** the type is unbounded; only resource exhaustion can
  fail.

In constant evaluation, undefined behavior makes the expression non-constant.
So does an exception that is not caught within the evaluation; since C++26,
exceptions may be thrown and caught during constant evaluation [@P3068R6]. An
out-of-range result that is undefined or escapes as an exception is therefore
a compile-time error.

**Where the policy lives.** The behavior on out-of-range results can be a
property of the *operation* or of the *type*:

- **Per operation:** a function applied to built-in types, such as
  `saturating_add` or `ckd_add`. The same values can be added differently at
  different call sites.
- **Per type:** a wrapper type whose operators all follow one policy.

**Conversions and mixed operations.** Conversions to and from other integer
types may be:

- implicit, including lossy conversions, as between the built-in types;
- implicit only when value-preserving, and explicit otherwise;
- checked at run time;
- explicit only.

Operations between different types may use the usual arithmetic conversions,
may produce a common type, or may be ill-formed.

**Object model:**

- a fundamental type or a class type;
- trivially copyable or not;
- fixed size, or allocating storage;
- usable in constant expressions;
- usable as a template argument;
- available in freestanding implementations.

A fundamental type takes part in the core language: in promotions, literals,
bit-fields, enumeration underlying types and `is_integral`. A class type
takes part only through overloading and library specializations
([How a class type participates]).

# Existing practice

## C

C23 ([@ISO-9899-2024]) changed C's integers in several ways that C++ has
followed or is considering:

- **Two's complement** representation is required [@WG14-N2412], as it has
  been in C++ since C++20.
- **Bit-precise integer types** `_BitInt(N)` and `unsigned _BitInt(N)`. They
  were added by [@WG14-N2709] in 2021 (the adopted text is [@WG14-N2763]),
  with literal suffixes `wb` and `uwb` [@WG14-N2775]. They are exempt from
  integer promotion. Their width can be anything up to the
  implementation-defined `BITINT_MAXWIDTH`, which is at least the width of
  `long long`. [@P3666R5] proposes them for C++.
- **`<stdckdint.h>`** provides `ckd_add`, `ckd_sub` and `ckd_mul`
  [@WG14-N2683]. They may not be used with bit-precise integer types
  [@WG14-N2867].
- **`<stdbit.h>`** provides bit utilities such as `stdc_count_ones`
  [@WG14-N3022].
- **`intmax_t`** need not represent the extended integer types wider than
  `long long` that `intN_t` aliases name [@WG14-N2888], or bit-precise
  types [@WG14-N3035].

C++26 takes C23 as its normative C reference [@P3348R4] and includes
`<stdckdint.h>` and `<stdbit.h>` [@P3370R1]. The first C2y working draft,
[@WG14-N3220], is freely available and differs from C23 only editorially. The
current C2y working draft [@WG14-N3998] goes further:

- it permits signed `_BitInt(1)` [@WG14-N3747];
- it allows bit-precise types as enumeration underlying types [@WG14-N3705];
- it adds `uabs` and related functions, whose results are always defined
  [@WG14-N3349].

## Compiler extensions

- **`__int128`.** GCC supports `__int128` and `unsigned __int128` "for targets
  which have an integer mode wide enough to hold 128 bits", and has no literal
  syntax for them ([GCC manual](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fint128.html)).
  Clang provides the same types. MSVC provides neither; [Implementation status]
  shows how each standard library treats `__int128`.
- **`_BitInt(N)`.** GCC accepts `_BitInt` in C but not in C++. Clang accepts it
  in both, in C++ as an extension
  ([Clang language extensions](https://clang.llvm.org/docs/LanguageExtensions.html)).
  The maximum width differs by compiler and target:

  | Compiler | Target | `BITINT_MAXWIDTH` |
  |:--|:--|--:|
  | GCC 16.2 | AArch64 | 65535 |
  | Clang 23.1 | x86-64 | 8388608 |
  | Clang 23.1 | AArch64 | 128 |
- **Overflow built-ins.** GCC and Clang provide `__builtin_add_overflow`,
  `__builtin_sub_overflow` and `__builtin_mul_overflow`. They "promote the
  first two operands into infinite precision signed type", store the result
  converted to the type of the third argument, and return whether the stored
  value differs. They therefore "have fully defined behavior for all argument
  values"
  ([GCC manual](https://gcc.gnu.org/onlinedocs/gcc/Integer-Overflow-Builtins.html)).
  C23's `ckd_add`, `ckd_sub` and `ckd_mul` have the same semantics, but take
  the result pointer first and accept fewer types.
- **MSVC intrinsics.** MSVC has no 128-bit integer type, but on x64 it provides
  wide multiplication (`_umul128`, `_mul128`, `__umulh`), division (`_udiv128`)
  and add-with-carry (`_addcarry_u64`, `_subborrow_u64`)
  ([MSVC intrinsics](https://learn.microsoft.com/en-us/cpp/intrinsics/x64-amd64-intrinsics-list)).
- **Code generation options.** These change the behavior of signed overflow
  in a whole translation unit
  ([GCC manual](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html)):
  - `-fwrapv` "instructs the compiler to assume that signed arithmetic overflow
    of addition, subtraction and multiplication wraps around using
    twos-complement representation".
  - `-ftrapv` "generates traps for signed overflow on addition, subtraction,
    multiplication operations".
- **Sanitizers.** Clang's UndefinedBehaviorSanitizer checks signed overflow,
  division overflow and invalid shifts. It also offers checks for behavior
  that is defined but "often unintentional": unsigned overflow
  (`-fsanitize=unsigned-integer-overflow`) and value-changing implicit
  conversions (`-fsanitize=implicit-conversion`)
  ([Clang documentation](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)).

# Observations

The survey shows several patterns. They are recorded here without
recommendations.

1. **Two vocabularies.** In the core language, "integer type" is a synonym
   for "integral type" and includes `bool` and the character types. Library
   wording uses "signed or unsigned integer type" for the arithmetic
   integers. Facilities differ in which they use. `gcd` accepts `char`,
   `saturating_add` does not, and `byteswap` accepts `bool`.

2. **The form of an overload set decides what it accepts.** A facility
   declared as a template restricted to a category accepts any new type added
   to that category. A facility declared as a fixed set of overloads accepts
   only the types it lists, plus those that promote to them. `to_string`,
   `abs` and iostreams have not been extended to extended integer types;
   `to_chars`, `<bit>` and saturation arithmetic have.

3. **Class types are integers only by convention.** Type traits and concepts
   are closed to program-defined types. The only class types the standard
   treats as integers are the implementation's integer-class types, which
   programs cannot define. Other class types join through specializable
   templates (`numeric_limits`, `hash`, `formatter`), through
   requirement-based facilities, or through functions in their own namespace.

4. **Implementations already extend the library to non-standard types, in
   different ways.** libc++ treats `_BitInt(N)` as integral, and most of its
   facilities accept widths up to 128 bits. libstdc++ does not treat it as
   integral. Both treat `__int128` as integral, but neither streams it or
   converts it with `to_string`. The MSVC STL provides neither type and uses
   an integer-class type where the others use `__int128`.

5. **The standard attaches overflow policy to operations.** `saturating_add`,
   `ckd_add`, `cmp_less` and `shl` apply a policy to built-in operands at one
   call. No standard integer type has operators that saturate, report, throw
   or widen. Types with such operators are found in libraries ([Libraries])
   and in proposals such as [@P2993R0].

6. **Every standard integer type has a fixed width.** The width is
   implementation-defined. Bounded-range types and unbounded types are found
   in libraries and proposals.

7. **Several facilities are limited to `long long`.** `intmax_t` need not
   cover wider extended types. `<random>` is not required to accept an integer
   type wider than `long long`, although libc++ and libstdc++ accept
   `__int128`. `to_string`, iostreams and `abs` stop at `long long`, and
   dynamic width in `std::format` accepts only standard integer types.
